## A. 部署模型与多项目管理（架构级，优先级最高）

### Q1. 守护进程与项目的对应关系
当前文档存在一个隐含矛盾：**架构图是单守护进程**，但数据模型又设计了 `projects` 表（暗示多项目），而全局配置只定义了**一个端口（19810）**。需要明确守护进程与项目的关系。

- **A. 单守护进程管理多项目**：一个 daemon 常驻，API 通过请求头/查询参数（如 `X-Project` / `?project=`）标识目标项目。→ 需额外设计项目切换与隔离。
- **B. 每项目一个守护进程实例（推荐）**：daemon 以 `--workdir` 启动并绑定该项目（呼应 AGENTS.md "所有路径基于用户传入的 --workdir 动态拼接"），APP 打开多项目 = 多 daemon 实例；`projects` 表仅记录"最近打开过的项目"历史，不承载运行时逻辑。

### Q2. 多实例端口冲突与端口管理
若采用 Q1-B：用户同时打开 2 个项目，第二个 daemon 绑定 19810 会冲突。

- **A. 端口自动分配（推荐）**：启动时若 19810 被占用则自动递增找空闲端口，实际端口写入该项目 `.taskboard/config.yaml`（或全局配置中的映射表），APP/CLI 据此连接。
- **B. 用户手动指定端口**：`--port` 参数，冲突时报错提示。
- **C. 不支持多项目并行**：一次只能打开一个项目（端口恒为 19810）。

### Q3. 项目列表管理
`projects` 表是否支持"移除项目记录"？（注意：移除记录 ≠ 删除 `.taskboard/` 目录数据）

- **A. 支持移除记录，数据保留（推荐）**：提供"从列表移除"功能，仅删 `projects` 行，磁盘数据不动；删除 `.taskboard` 目录必须由用户手动完成。
- **B. 不做项目列表**：项目切换完全由用户选择目录触发，不持久化历史。

## B. 任务与数据模型

### Q4. 状态机流转规则的定义位置
文档提到状态（待办/进行中/已完成/已归档），Skill 文件又说包含"状态机流转规则"，但**没说明状态机是硬编码还是可配置**。这直接影响 service 层实现（AGENTS.md 要求 `ChangeStatus` 在 service/task.go 内）。

- **A. v1 硬编码四态 + 最小校验（推荐）**：状态机逻辑写死在 service 层；允许 待办→进行中→已完成→已归档 及回退；Skill 仅描述状态语义，不驱动流转逻辑。自定义状态留 v2。
- **B. 状态机可配置**：由 `.taskboard/config.yaml` 或 Skill 文件定义流转规则，service 动态读取。→ 实现复杂度显著上升，需额外设计规则校验。

### Q5. 任务删除语义
文档未定义删除行为。AGENTS.md 规定：删父任务时子任务**软删除或置空 parent_id**，禁止物理删除子任务；但"任务删除"本身是软删还是物理删未定义。

- **A. 软删除（推荐）**：任务增加 `status=deleted`（或单独 `deleted_at` 字段），列表默认过滤、可恢复、审计可追溯；父任务删除时子任务**级联置空 parent_id**（保留为顶层孤儿，避免误删子任务内容）。
- **B. 物理删除 + 级联软删子任务**：父任务物理删除，子任务软删。

### Q6. depends_on 循环依赖与引用清理
AGENTS.md 要求 Update 必须校验循环依赖，文档未提。

- **A. 写操作时拒绝（推荐）**：Create/Update 时若 `depends_on` 引入环，返回明确错误拒绝写入；删除任务前检查是否有任务依赖它，若有则报错提示（由用户解除依赖或确认级联解除）。
- **B. 允许写入 + 标记警告**：环可保存，但 API 返回 `warning` 字段，全景地图中红色高亮。

### Q7. priority 0-5 的语义与排序
- **A. 0=无优先级/默认，5=最高（推荐）**：排序规则为 priority 降序 → created_at 升序；无优先级任务排最后。
- **B. 0=最低，5=最高**：所有任务都显式参与排序。

### Q8. assignee 字段
- **A. 自由文本（推荐，符合本地单机定位）**：不做成员管理，仅字符串展示与过滤。
- **B. 成员管理**：需要用户/成员 CRUD + 校验。→ 明显超出"本地优先"定位，不推荐。

### Q9. tags 字段
- **A. 自由标签 + 过滤（推荐）**：字符串数组，仅支持按标签过滤/搜索，不做全局标签管理（重命名/颜色）。
- **B. 标签管理**：需要标签字典、颜色、重命名合并。→ 留 v2。

### Q10. 数据规模与全景地图渲染上限
- **A. 单项目任务量级预期（推荐填写）**：请确认目标量级（100 / 1,000 / 10,000+ 条）。这决定是否需要分页与图渲染优化。
- **B. 全景地图渲染上限**：节点数超过阈值（建议 2,000）时自动聚簇/分片渲染，避免卡顿——是否接受？

## C. LLM 导入 / 导出

### Q11. 导入流程是否设"确认环节"
LLM 解析结果直接入库，还是先进入"草稿预览"由用户核对？

- **A. 直接入库 + 审计（推荐 v1）**：解析成功即入库；解析失败返回明确错误且**不落库**（符合 AGENTS.md "缺 title/status 必须拒绝"），用户在 UI 修正原文档后重新导入。
- **B. 草稿确认**：先写入 `draft` 状态，用户确认后才转为正式任务。→ 多一套状态与界面，v1 不建议。

### Q12. 同一文件重复导入策略
- **A. 文件级全量覆盖（推荐 v1）**：以 `source_file` 为同步单元，重新导入 = 删除该文件来源的全部旧任务后按新结果重建（可先软删、确认成功后再清）；无匹配可增量合并逻辑。
- **B. 按标题/ID 增量合并**：需要定义匹配键与冲突策略，复杂度高，v2 再说。

### Q13. 手动修改原 Markdown 后的数据同步方向
文档明确"库 → MD 不自动写回"，但 **MD → 库** 的方向需确认：

- **A. 单向显式同步（推荐）**：一切变更都必须通过显式"导入/导出"动作；用户手动改 MD 后，库内数据不会感知，直到再次显式导入。无自动监听文件变化。
- **B. 自动监听文件变化**：文件改动后自动触发解析。→ 与"不自动写回"不对称，且引入文件监听复杂度，不推荐。

### Q14. LLM 配置项
- **A. 确认配置项集合（推荐）**：接口地址、API Key、模型名、超时（默认 60s）、重试次数（默认 1）、max_tokens（默认 4096）、请求并发数（默认 1）；必须支持 OpenAI 兼容接口。
- **B. 本地模型（Ollama / llama.cpp）是否纳入 v1 验收范围？** 建议：纳入（OpenAI 兼容协议本身即可覆盖 Ollama）。

### Q15. 解析失败与部分失败处理
- **A. 整体失败，不落库（推荐）**：单文件解析任一环节失败（JSON 不合规 / 缺关键字段）→ 整次导入失败，返回错误信息 + LLM 原始输出，供排查。无"部分成功"状态。
- **B. 部分成功**：逐任务落库成功项，失败项返回列表。→ 增加一致性复杂度，不推荐 v1。

### Q16. 导出默认模板草案确认
默认模板需要确认结构，建议 v1 草案如下，请确认或修改：

```markdown
---
title: "{{project_name}}"
generated_at: "{{timestamp}}"
---

# {{任务标题}}   <!-- 按层级决定标题级别：顶层 ##，子任务逐级 +# -->

- [ ] **待办** | 优先级: {{priority}} | 标签: {{tags}} | 负责人: {{assignee}}
- [ ] 描述文本……

## 子任务1
- [ ] ...
```

- **A. 采用草案（推荐）**：Front Matter 含项目名/生成时间；任务用标题层级表达父子关系；状态映射为 checkbox（待办=`[ ]`、进行中=`[~]`、已完成=`[x]`、已归档=折叠到注释）。
- **B. 需要调整**：请指出需要修改的部分。

## D. 权限与安全

### Q17. Actor 身份可伪造性
文档定义 actor 识别优先级：`X-Actor` 头 > MCP 客户端名 > CLI 执行者 > unknown。**`X-Actor` 是明文头，可被任意 curl 伪造**。本地回环可信（假设本机无恶意进程），但**远程访问开启后**必须有更强机制：

- **A. 远程必须配置 API Token（推荐）**：全局配置增加 `api_token`；远程连接（非回环）必须携带 Token，本地回环免 Token。Token 同时充当 actor 绑定凭证。
- **B. v1 不做 Token**：远程访问开启后仍信任 `X-Actor`。→ 安全风险，不推荐。

### Q18. 权限维度：是否区分 human / agent 两套权限
文档权限表是 `(project, action, allowed)` 的单一维度，但产品核心是"AI 以等价权限操作"且"AI 不可修改自身权限"——隐含存在**两类主体**。

- **A. 增加角色维度（推荐）**：permissions 表结构改为 `(project, actor_role[human|agent], action, allowed)`，human 与 agent 各一套开关；默认 human 全开、agent 只读（read=true，其余 false）。
- **B. 单一维度**：所有非 human 的请求统一视为 agent，共用一套开关。→ 无法实现"human 可写、agent 只读"的默认态，不推荐。

### Q19. 权限修改通道
"所有权限设置只能由用户通过 APP 配置界面完成"——CLI 是否也允许修改权限？

- **A. 仅 APP GUI 可修改权限（推荐）**：CLI/MCP/API 完全不提供权限修改端点（只有查询）；GUI 修改时额外校验请求来源为回环。彻底封死伪造路径。
- **B. CLI 交互式修改**：需要额外身份验证（密码），复杂度高，不推荐 v1。

### Q20. 远程访问开启后的传输安全
- **A. 明文 HTTP + Token（推荐 v1）**：远程访问默认仅建议内网使用；TLS 留 v2（需证书管理）。
- **B. 必须 TLS**：增加证书配置项与自签证书生成流程。

## E. Skill 与 Agent 引导

### Q21. Skill 文件格式与解析
文档说"YAML/Markdown"，但未定义结构。

- **A. 双格式支持 + schema 草案（推荐）**：YAML 作为结构化格式，Markdown 作为纯描述格式（转成 content 文本）；YAML schema 草案：
  ```yaml
  name: taskboard-basic
  version: 1
  description: 任务操作指引
  instructions: |
    使用 task_read / task_create 等工具……
  ```
  解析失败仅告警不阻断 daemon 启动。
- **B. 仅 YAML**。

### Q22. "MCP 工具集随 Skill 动态丰富"的实现边界
MCP 协议中工具列表在**会话初始化时声明**，运行时热注册会破坏客户端状态。需要明确 v1 边界：

- **A. v1 工具集固定（推荐）**：MCP 暴露固定核心工具集（task_read/task_create/task_update/task_delete/import/export/skill_info 等）；Skill 仅提供**描述性引导**（skill_info 返回结构化文本），不动态注册新工具；动态工具留 v2（且需重启 MCP 会话生效）。
- **B. v1 就做动态注册**：需要自研 MCP 工具管理 + 会话重启通知机制，复杂度极高，不推荐。

### Q23. skills 数据源统一（文档内部矛盾）
目录结构有 `.taskboard/skills/` 文件目录，数据模型又有 `skills` 表（name, content）——**双存储冗余**。

- **A. 文件系统为唯一数据源（推荐）**：以 `skills/` 目录文件为准，`skills` 表仅做索引/缓存（供 skill_info 快速查询），启动时扫描目录同步。
- **B. 数据库为源**：文件导入后进表，删除文件不影响。→ 与"本地优先、文件自包含"理念不符，不推荐。

### Q24. AGENTS.md 与 skills/ 的分工
- **A. 分工确认（推荐）**：`AGENTS.md`（项目根目录）回答"**何时**调用 taskboard 工具"（场景判断）；`skills/` 回答"**如何**操作"（工具用法、字段语义）。两者不合并，内容由用户编写，daemon 只提供 skill_info 查询能力。
- **B. 需要 daemon 解析 AGENTS.md**：→ 不推荐，AGENTS.md 是给 AI 助手的提示词文件，非机器数据。

## F. 实时性与 API

### Q25. WebSocket 事件范围与订阅过滤
- **A. 事件全集 + 按项目过滤（推荐）**：事件类型：`task.created/updated/deleted/status_changed`、`import.progress/complete/failed`、`export.complete`、`permission.changed`、`skill.changed`；连接建立时通过查询参数（`?project=`）订阅指定项目；远程连接需 Token（同 Q17）。
- **B. 仅任务变更事件**：权限/skill 变更由客户端轮询。

### Q26. GET /api/tasks 的返回结构与分页
- **A. 树形返回 + 查询参数（推荐）**：默认返回完整任务树（嵌套 children）；支持 `?filter[status]=`、`?q=`（标题/描述搜索）、`?page=&size=`（层级扁平化时分页）；单项目任务量 < 5,000 时不分页。
- **B. 平铺列表 + 客户端组装树**：→ 前端组装成本高，不推荐。

### Q27. 并发写冲突策略
多端同时修改同一任务：
- **A. 最后写入生效 + 审计记录（推荐 v1）**：不加乐观锁，靠审计日志追溯。实现最简单，符合本地单用户定位。
- **B. 乐观锁（updated_at 比对）**：冲突返回 409，客户端重试。→ v2 可加。

## G. CLI / 守护进程 / 打包

### Q28. CLI 与守护进程的生命周期
CLI 执行命令时若 daemon 未运行：
- **A. CLI 报错提示（推荐）**："daemon 未运行，请先执行 taskboard daemon --workdir <dir> 启动"，并提示定位方式（默认 `127.0.0.1:19810`，`--port` 覆盖，或从项目 config 读取实际端口）。CLI 不做进程拉起（保持单二进制纯净职责）。
- **B. CLI 自动拉起 daemon**：需要内嵌进程管理，复杂且易出现僵尸进程，不推荐。

### Q29. APP 与守护进程生命周期
- **A. APP 退出即关闭 daemon（推荐 v1）**：APP 内嵌 daemon，随 APP 生命周期启动/退出；CLI 使用时用户手动起 daemon（或未来提供系统服务安装选项）。
- **B. daemon 常驻**：APP 退出后 daemon 保持运行，支持后台任务。→ 需要托盘/服务管理，v2。

### Q30. 全局配置热加载
端口 / remote_access / LLM key 修改后：
- **A. 需重启 daemon 生效（推荐 v1）**：改配置后提示"重启生效"；remote_access 切换同理。

## H. 文档内部矛盾与一致性

### Q32. 审计日志双存储矛盾（必须解决）
目录结构写 `audit.log` 文件，数据模型又定义 `audit_log` 表——**同一份数据两个去处**。

- **B. 纯文件**：仅追加写 `audit.log`，不做表。→ 无法在 APP 内查询审计，不推荐。

### Q33. 模块命名统一（文档 vs AGENTS.md）

- **B. 以需求文档为准**：重构 AGENTS.md。→ 不推荐，AGENTS.md 已含详细约束。

### Q34. 审计完整性
AGENTS.md 要求所有写操作（含 Import/Export）异步写审计日志：
