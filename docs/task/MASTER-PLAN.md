# TangoForge 主行动计划（Master Plan）

> **版本**：v1.0（2026-08-05）
> **定位**：本文件是 TangoForge 从「骨架初始化」走向「可交付 v1」的**战略路线图**，回答"做什么、按什么顺序做、做到什么程度算完成"。
> **配套文档**：
> - 可执行任务清单：`docs/task/TASKS.md`（每个任务的操作细节）
> - 任务全景预览：`docs/task/OVERVIEW.md`（任务看板 / 进度追踪）
> - 权威基线：`AGENTS.md`（约束）→ `docs/REQUIREMENTS.md`（需求）→ `docs/TECHNICAL.md`（技术落地），冲突以 REQUIREMENTS.md 为准

---

## 1. 计划目标

在既有骨架（数据库未建、业务层仅模型、守护进程仅 `/ping`、前端仅目录骨架）的基础上，**分 6 个阶段、31 个任务**（`TF-001` ~ `TF-031`），按依赖顺序逐步实现 TangoForge v1：

1. **数据层**：SQLite 全表自动创建、配置双层次加载与热重载、守护进程常驻骨架；
2. **任务核心域**：任务 CRUD + 项目级状态机 + 归档/还原 + 依赖无环校验，覆盖率 ≥ 90%；
3. **传输层与安全**：来源识别、权限中间件、异步审计、HTTP API 与 WebSocket 全端点；
4. **Agent 能力**：LLM 客户端、MCP 固定工具集、Markdown 导入（草稿流）与导出、Skill 索引、CLI；
5. **前端应用**：shadcn-ui 基础、路由与 API/WS 封装、项目管理、看板、任务编辑、导入导出 UI、全景地图、权限/Skill 界面；
6. **测试与交付**：集成测试、CI 质量门禁、6 平台交叉编译与打包验证。

每个任务完成标准遵循 `AGENTS.md §10.6`：代码落位正确、测试齐备、`make check` 通过、文档同步更新、**并按 `AGENTS.md §13` 产出任务总结与任务日志**。

## 4. 任务编号与依赖规范

### 4.1 编号规范（全项目唯一）

- 格式：`TF-XXX`（TangoForge 任务，三位数字顺序编号）。
- 编号一经分配**不因顺序调整而复用/变更**；任务废弃时在 `TASKS.md` 标记 `废弃` 并说明原因，编号保留。
- 任务总结 / 任务日志 / 提交信息中必须引用任务编号（见 §6 与 `AGENTS.md §13`）。

### 4.2 任务字段（TASKS.md 中逐条维护）

`编号 / 标题 / 阶段 / 优先级(P0-P2) / 依赖 / 描述 / 验收标准 / 涉及模块 / 状态 / 总结文件`

- **P0** = 阻塞后续多数任务（如 db 迁移、daemon 骨架）；**P1** = 常规；**P2** = 可延后（如 LLM 生成模板、全景图优化）。

### 4.3 关键依赖链（主线）

```
TF-001 db迁移 ──► TF-005 task CRUD ──► TF-010 auth ──► TF-013 HTTP核心API ──► TF-016 MCP框架 ──► TF-022 前端基础 ──► TF-029 集成测试 ──► TF-031 打包
TF-002 配置 ────► TF-003 daemon骨架（依赖 db+config）┘
TF-004 项目管理（依赖 db）────────────────┘
TF-006~008（依赖 TF-005）──► TF-009 覆盖率收口 ┘
TF-011 权限（依赖 TF-010）──► TF-012 审计（依赖 TF-010）
TF-014 WS（依赖 TF-013 + TF-012）
TF-015 LLM（独立）──► TF-018 parser / TF-019 exporter（依赖 LLM + TF-004/TF-005）
TF-017 MCP 工具全集（依赖 TF-016 + 业务层各模块）
TF-020 skill（依赖 TF-005）
TF-021 CLI（依赖 TF-013 端点就绪）
TF-023~028（依赖 TF-022 前端基础 + 对应后端端点）
TF-030 CI（依赖绝大部分任务完成）
```

详细依赖图见 `docs/task/OVERVIEW.md` §3。

## 5. 执行策略（如何逐步完成）

### 5.1 推进节奏（vibe coding 工作流）

1. **一次只做一个任务**：从 `TASKS.md` 中取当前「依赖已满足且状态=待开始」的 P0/P1 任务，编号最小的优先。
2. **遵守开发流程**：切分支（`feat/TF-XXX-<slug>`）→ 实现 → 自测 → `make check` 对应项 → 更新 `TASKS.md` 状态与 `OVERVIEW.md` → 写日志/总结 → 提交（Conventional Commits，subject 带 `TF-XXX`）。
3. **完成定义（DoD）**，必须同时满足：
   - [ ] 代码落在正确模块（AGENTS.md §9），遵守分层铁律（§3.2）；
   - [ ] 业务层附带 `_test.go`（§8），关键路径补集成测试；
   - [ ] 本地执行对应质量命令并**贴出结果**（§10.4）；
   - [ ] 前端改动同步 `app/src/types/` DTO；
   - [ ] `docs/task/TASKS.md` 状态置为 `已完成`，`docs/task/OVERVIEW.md` 统计同步；
   - [ ] 产出 `docs/record/TF-XXX-<标题>-<结果>.md` 任务总结；
   - [ ] 产出 `docs/log/TF-XXX-<标题>.md` 任务日志（临时任务豁免，见 §6.3）。

### 5.2 并行度建议

- 同一阶段内、无依赖关系的任务可并行（如 P4 中 TF-015 LLM 与 TF-020 Skill 互不依赖）。
- **禁止跨阶段跳做**：P2 未收口（覆盖率 < 90%）前不进入 P3 的 API 全量开发，避免在未稳定的业务层上堆传输层。

### 5.3 风险任务前置

- `TF-001`（db 迁移）与 `TF-003`（daemon 骨架）为 P0，先行攻坚，因为它们被多数任务依赖。
- `TF-009`（覆盖率收口）在 P2 末尾强制执行，避免测试债滚入后续阶段。
- `TF-030`（CI）从 P1 起即应部分落地（backend-ci 先跑 db/config/task），不要留到最后一次性验证。

## 6. 任务记录体系（docs/record · docs/log）

> 本项目工作流要求（已固化进 `AGENTS.md §13`）：**任务总结必写、任务日志按需写、临时任务豁免**。

| 目录 | 内容 | 命名 | 必写？ |
|------|------|------|--------|
| `docs/task/` | 计划三件套：主行动计划 / 可执行任务清单 / 任务全景预览 | 固定文件名 | 维护更新 |
| `docs/record/` | **任务总结**：该任务做了什么、结果如何、遗留问题 | `TF-XXX-<任务标题>-<结果>.md`，结果 ∈ `成功 / 失败 / 部分完成` | ✅ 每个正式任务完成后必写 |
| `docs/log/` | **任务日志**：工作过程中的过程记录（进展、决策、踩坑） | `TF-XXX-<任务标题>.md`（可追加多日内容） | ⚠️ 正式任务进行中记录 |
| `docs/README.md` | docs 目录使用说明 + 文件索引 | 固定文件名 | 维护更新 |

**临时任务豁免**：以下与修改源代码无关的任务**不需要**任务日志（但涉及可复用结论时仍建议一句话记入当日 `docs/log/` 根文件或项目 MEMORY）：

- 修改配置文件（如 `.golangci.yml`、`app/package.json` 依赖版本）；
- 临时对代码进行验证（跑一次测试、起一次服务、查一次数据）；
- 纯只读操作（阅读文档、检索代码、代码审查结论记录除外）。

**总结文件模板**（写入 `docs/record/`）：

```markdown
# TF-XXX <任务标题> — 任务总结
> 结果：成功 / 失败 / 部分完成　|　日期：YYYY-MM-DD　|　执行人：<ai|human>

## 1. 任务范围
（一句话：本任务交付了什么）

## 2. 交付内容
- 新增/修改的文件清单（路径）
- 关键实现点（≤5 条）

## 3. 验证结果
- 命令与输出摘要（测试 / 覆盖率 / lint）
- 冒烟结果

## 4. 遗留问题与后续
（未完成项、已知风险、下一步建议；无则写"无"）
```

## 8. 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| `modernc.org/sqlite` 纯 Go 约束导致迁移写法受限 | 迁移实现慢 | TF-001 先行试点，先用 `sqlite:memory:` 跑通 DDL 再接入文件库 |
| 权限/来源识别边界理解偏差 | 安全漏洞或误伤 UI | TF-010 严格按 `REQUIREMENTS.md §7.2` 5 级判定实现 + 集成测试覆盖 denied 路径 |
| 状态机可配置化复杂度超预期 | P2 延期 | 先按默认四态实现并抽 Interface，配置化作为 `config.yaml` 读取扩展（不影响既有流转） |
| 前端 shadcn-ui + React 19 生态版本坑 | 初始化卡顿 | TF-022 首日攻坚，锁版本；失败回退 Radix 原语直用（仅限 ui/ 封装层内） |
| 覆盖率门槛在 CI 上因环境差异失败 | CI 红 | `check_coverage.sh` 支持 `THRESHOLD` 覆盖，本地与 CI 统一阈值 |
| 任务计划本身漂移 | 计划与代码脱节 | 每次任务完成后同步 TASKS.md / OVERVIEW.md；计划变更走 §9 变更控制 |

## 9. 变更控制

- **增删任务**：在 `TASKS.md` 末尾追加新编号或标记废弃，同步更新 `OVERVIEW.md` 与本文档（如阶段/里程碑变化）。
- **范围变更**（影响 REQUIREMENTS 语义、状态机、API 格式）：先与用户确认，再更新需求/技术文档，最后落到任务清单。
- **优先级调整**：仅更新 `TASKS.md` 优先级字段与 `OVERVIEW.md` 排序，不重排编号。
